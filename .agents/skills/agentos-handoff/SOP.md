# Handoff and resume SOP

## Inputs and entry

Active objective, latest relevant brief/handoff, current repository/revision, acceptance criteria, completed evidence, approvals, explicit pauses/stops and queued ideas. A historical handoff is context, not proof of current deployment/provider state.

## Permitted actions

Read relevant current sources, produce a sanitized handoff, resume authorized incomplete work, and recheck only material drift. Reuse stable completed work instead of recreating it.

## Prohibited actions

Do not dump private conversations, secrets or raw provider payloads; restart already-complete work; discard pending constraints; infer approval from a previous agent's claim; create another chat, message others, delegate, deploy or release merely because a handoff exists. Do not resume explicitly paused work without the user's instruction.

## Procedure

1. Recover the intended outcome and scope before acting. Compare the handoff revision with current files/tree, and distinguish facts from proposals.
2. Identify completed work and check validity. Recheck changeable state only where it affects the next action; do not rerun the whole prior workflow.
3. Preserve existing authorization limits. List blocking decisions and the work they hold; keep independent next actions concrete.
4. Carry queued ideas, including Antigravity feasibility when still pending, without silently implementing them or replacing the active assignment.
5. For resume, proceed with the next authorized incomplete step. For handoff, use the short task-brief fields and link evidence rather than copying full histories.
6. If a separate chat is useful, suggest it. Create or send a handoff only when explicitly authorized and the intended destination is clear.

## Stop or hold

Respect explicit pause/cancel and superseding priorities. Hold on conflicting current state or missing critical permissions; ask a focused question and continue only independent authorized work.

## Exit and evidence

State actual changes, reusable checks/revision, limitations, pending approvals, next action, queued separate tasks and Git/push state. Mark complete only when acceptance criteria are met; otherwise use the precise active/held/paused/superseded state.
